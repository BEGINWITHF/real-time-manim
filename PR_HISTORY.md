### #137 — fix: keep FramePreview alive when stdin is not interactive

`fix/preview-no-tty` · merge `8da20c27f5`

<details><summary>PR description</summary>

Implements the FramePreview/no-TTY item from the post-2.0.11 feedback (B4).

`TerminalInput` treated **EOF** as a quit command.  A detached launch (or
`--no-bar` with no console) therefore read EOF immediately, queued `q`, and
killed the preview before the window could be used.  This is the second half of
the slider failure: if the native bar cannot be created and stdin is not
interactive, there was nothing left.

- `EOFError` now only stops the stdin reader.  The window stays open on its own
  until the user closes it.
- `Ctrl-C` still sends quit.
- `stdin_is_tty()` avoids starting the reader when `sys.stdin` is missing.
- `run()` logs the no-input state instead of silently falling into a dead
  terminal.

## Verification

- `python -m real_time_manim.preview demo:Demo --no-bar --quiet` with
  `stdin=subprocess.DEVNULL`: still running after 3.5 s; before this change it
  exited immediately (EOF -> `q`).
- Direct `TerminalInput` probe with `input()` raising `EOFError`: no callback,
  reader stops.
- `stdin_is_tty()` with a fake non-TTY stream: False.
- `tests/test_preview_spec.py`: 20 passed.

No native changes, no version bump.

</details>

### #139 — perf: indexed MeshBatch vertices, unique projection and buffer reuse

`perf/mesh-indexed` · merge `8bd2035826`

<details><summary>PR description</summary>

Part A2 of the post-2.0.11 feedback.  A1 (`MeshBatch.from_surface`) will build
on this representation; kept separate so the projection change is reviewable
on its own.

## What changed

`MeshBatch` only stored explicit quads, so `build_vertices` expanded every quad
to six triangle corners and projected the same shared corner up to six times.
An 18,432-quad grid has 18,705 unique vertices but **110,592** expanded corners.

- `append_indexed(vertices, quads, colors=None)` stores unique `(N, 3)`
  vertices plus `(Q, 4)` indices and per-corner colours.
- `build_vertices` projects the unique vertices once and gathers the two
  triangles per quad.  The gathered output buffer is reused across frames.
- For an indexed batch, both the gathered triangles and the projection are
  cached until `_geometry_rev` or the view changes (`mark_geometry_dirty()`
  covers in-place vertex edits).
- `append()` and `append_indexed()` cannot be mixed in one batch; `append`
  keeps its exact old output (verified against the pre-change module).

## Measurements (144x128 grid = 18,432 quads / 18,705 unique / 110,592 expanded)

| build | ms |
|---|---:|
| `append` (explicit quads) | 13.4 |
| `append_indexed` (new view each build) | **4.45** |
| `append_indexed` (same view, cached) | **0.04** |

The feedback's 17.9 ms is the same shape; this machine is a little faster.
Native still receives expanded vertices — an index buffer/`vkCmdDrawIndexed`
is a later native step.

## Verification

- indexed output is byte-identical to `append` for the same grid (`max diff 0`);
- rendered indexed mesh vs its append twin: byte-identical on two frames;
- current `append` output vs the pre-PR module: max diff 0;
- `tests/test_mesh_indexed.py`: 5 passed (equality, offsets, cache
  invalidation, mixing rejected, default colours);
- `tests/test_depth_mesh_auto.py` + depth paint-order tests: 14 passed.

Docs: `RTM-Wiki/agent/three-d.md` now documents `append_indexed`,
`mark_geometry_dirty`, the no-mixing rule and the measured costs.

No native change; no version bump.

</details>

### #141 — perf: MeshBatch.from_surface bakes a flat Surface; warn on dense painter surfaces

`feat/mesh-from-surface` · merge `2c314b111a`

<details><summary>PR description</summary>

Part A1 of the post-2.0.11 feedback.  A2 (`append_indexed`, #139) gave
`MeshBatch` unique vertices and a reused projection buffer; this PR makes an
ordinary `Surface` reach that path in one call, and warns once when a dense
surface stays on the painter.

## What changed

### `MeshBatch.from_surface(surface, *, ignore_strokes=False)`

```python
surf = Surface(...)
surf.set_shade_in_3d(False)   # the mesh carries flat colours
surf.set_stroke(width=0)      # the mesh does not stroke face outlines
win.set_mesh(MeshBatch.from_surface(surf))
```

- Reads each face's four `points[::4]` anchors (the same corners the
  `RTM_AUTO_DEPTH` prototype uses), deduplicates to unique vertices and appends
  one indexed quad per face with the face's fill colour.
- Supported subset is explicit and fails loudly with the face index: opaque
  faces (`fill_opacity >= 0.999`), `shade_in_3d=False`, 3-4 corners, a flat
  fill.  A visible stroke raises unless `ignore_strokes=True` (one
  `RuntimeWarning`); transparency and shading are rejected rather than silently
  drawn wrong.
- The bake is a snapshot in world space: camera moves follow it, later
  `Surface` transforms/colour changes do not.  Docs say to rebuild or edit the
  arrays plus `mark_geometry_dirty()`.
- Do not `self.add` the same surface: the mesh replaces its painter drawing.
  If the mobject must stay in the scene, bake first and then
  `surf.set_opacity(0)` (verified pixel-identical to mesh-only).

Extraction has a vectorized path for the normal uniform 4-corner grid
(`points[::4]` for the whole surface) and falls back to the per-face ring for
irregular cells (degenerate pole cells, 3-corner rings).  The first version paid
`get_start_anchors()` + `np.allclose` per face: 9,800 faces took ~460 ms; the
uniform path bakes them in ~73 ms.

### Dense-surface hint

`window/core.py` calls `depth_mesh.warn_dense_surface(roots, scene)` when a 3D
frame has no explicit mesh and `RTM_AUTO_DEPTH` is off.  A `Surface` with
`DENSE_SURFACE_FACES = 2000` or more faces gets one `RuntimeWarning` per scene
pointing at `MeshBatch.from_surface` / `RTM_AUTO_DEPTH=1`.  It does not change
rendering.

## Measurements

9,800-face lathe surface (checkerboard fills, `shade_in_3d=False`), 1920x1080
`FrameServer.save_frame`:

| path | first frame | steady frames |
|---|---:|---:|
| painter | 1,303 ms | 182-194 ms |
| `MeshBatch.from_surface` | 53 ms | 31-39 ms |

`from_surface` bake: 400 faces 1.6 ms, 3,600 faces 14 ms, 9,800 faces 73 ms.
`build_vertices` after bake: ~1.5-3.4 ms when it must re-project, ~0.04 ms when
the view is unchanged.  The mesh also fixes the painter's self-occlusion: the
lathe's front wall is missing in the painter frame and whole in the mesh frame
(see attached screenshot).

## Verification

- painter vs mesh on a height-field surface (interior pixels): identical;
  every differing pixel is within 1 px of the mask edge (per-face antialiasing),
  and the solid-fill comparison has zero differing *interior* pixels;
- `tests/test_mesh_from_surface.py`: 8 passed (quad count, checkerboard
  colours, fast/slow path equality, shaded/transparent/stroke/non-surface
  rejection, dense warning once per scene);
- `test_depth_mesh_auto.py`, `test_paint_order*`, `test_plot_surface.py`,
  `test_static_layer.py`, `test_three_d_camera_zoom.py`: 72 passed;
  `test_random_nested_z_index_trees` fails identically on unmodified
  `origin/main` (pre-existing, unrelated);
- Sphere / Torus / Cylinder / 3,600-face Surface all bake (slow path where
  cells are degenerate);
- mesh-only vs mesh + `set_opacity(0)` surface: max pixel diff 0;
- mesh-only vs mesh + visible surface differs, as the docs warn.

Docs: `RTM-Wiki/en_US/06-Three-Dimensional/02-Surfaces.md`,
`RTM-Wiki/agent/three-d.md`, `RTM-Wiki/agent/runtime.md`.

No native change; no version bump.  `MeshMobject` (vertex-level transforms) is
the follow-up step on this representation.

### #143 — perf: cache per-face 3D shading, scalar shading arithmetic

`perf/3d-shade-cache` · merge `af482a530b`

<details><summary>PR description</summary>

Part A3 of the post-2.0.11 feedback.  Shading a 9,800-face `Surface` cost
~1.86 s/frame inside `shaded_fill_rgb` + `shaded_fill_gradient`, which made a
shaded 3D scene several times slower than the same scene with
`set_shade_in_3d(False)`.

## What changed

`real_time_manim/render/util.py`:

- **Per-face shade cache** (`_lit_corner_colors`): a face's two lit corner
  colours depend on its own points, its fill and the **world** light source —
  never on the camera.  Both `shaded_fill_rgb` (single colour for stroke/polygon
  paths) and `_shaded_face_gradient` (the two gradient stops) asked for the same
  pair separately, so each send computed four corner normals instead of two,
  every frame.  The pair is now computed once and stored on the mobject, keyed
  on `points`/`fill_rgbas`/light bytes; an orbiting camera reuses it and only
  the two projected gradient endpoints are redone.  Editing points, changing the
  fill or moving the light invalidates it automatically.
- **Scalar shading arithmetic**: `_shade_one` and `_unit_normal` replaced
  `np.linalg.norm` / `np.dot` / `np.cross` on three-element vectors.  `np.cross`
  alone costs ~55 µs per call through `moveaxis`/`normalize_axis_tuple`; a face
  needs two.  The multiply-add order is unchanged.
- The `np.clip(...)*255` tails became scalar clamps, also order-preserving.

## Measurements

9,800-face shaded lathe `Surface` (checkerboard fills, default
`shade_in_3d=True`), 1920x1080 `FrameServer`, camera orbited between frames
(every send is a cache miss, which is the expensive real case):

| | per frame |
|---|---:|
| before | 3.4–4.2 s |
| after | **1.5–1.6 s** |

Per-face shading cost (`shaded_fill_rgb` + `shaded_fill_gradient` together):
**190 µs → 22–27 µs** per face.  With a static camera the whole send is
replayed as before, so those frames are unchanged by design.

## Verification

- Shading **values** compared against the unmodified `origin/main` module:
  3,558 faces across Cube, Sphere, Torus, Cylinder, Cone, Prism, Tetrahedron,
  Octahedron × 3 camera/light setups → **0 differences** for both
  `shaded_fill_rgb` and `shaded_fill_gradient` (including the 4-point-face and
  two-stop-fill edge cases).
- Rendered a Sphere + Cube + Torus 3D scene on both modules: two frames,
  **byte-identical** (max pixel diff 0).
- New `tests/test_shade_cache.py` (7 passed): manual-value equality,
  one shading computation feeding both consumers, orbit hits the cache, light /
  points / fill changes invalidate, 2D viewport is a no-op.
- Camera / paint-order / surface / mesh suites: 75 passed.

Docs: `RTM-Wiki/agent/three-d.md` gains the shading-cost note.

No native change; no version bump.  Next, if this PR lands, the remaining
per-face cost is the per-face `AddBezierPath` send itself (~1.5 s for 9,800
faces while orbiting); batching it would need a gradient-capable native batch
(`AddPolygon` carries one colour), so that is a separate native step.

</details>

### #144 — feat: native bloom + tonemap post-processing

`feat/post-bloom-tonemap` · merge `9cbac7f035`

<details><summary>PR description</summary>

Second roadmap slice of the full-film feedback: bloom/tonemap.

## What it does

An opt-in pass inside the frame's command buffer, **after** the scene resolves and **before** screenshot readback/present:

1. copy the swapchain image into a sampleable texture
2. soft-knee bright pass at half resolution (2x2 box downsample)
3. separable Gaussian blur, H then V, on a half-res ping-pong pair
4. composite `scene + bloom * strength` with exposure and an optional ACES/Reinhard curve back into the swapchain

The existing scene render pass, MSAA resolve and painter/mesh pipelines are untouched. With post off (default) no copy and no pass are recorded.

## API

```python
win.set_post(bloom=0.9, threshold=0.65, exposure=1.0, tonemap="aces")
win.set_post(False)     # keeps the look for a later re-enable
```

| parameter | default | meaning |
| --- | --- | --- |
| `bloom` | 0.6 | blurred highlight added |
| `threshold` / `knee` | 0.82 / 0.12 | bright-pass luma and soft edge |
| `exposure` | 1.0 | multiplier before the curve |
| `radius` | 1.6 | blur radius in half-res texels |
| `tonemap` | `none` | `none`, `aces`, `reinhard` |

No-code opt-in: `RTM_POST=1` (or `RTM_POST=aces`) plus `RTM_POST_BLOOM/THRESHOLD/KNEE/EXPOSURE/RADIUS/TONEMAP` overrides. `RTM_DIAGNOSTICS=1` now reports `post=on/off` per play.

## Verification

- `bloom=0 / tonemap=none` vs post off: **max channel diff 0** (copy+composite is an identity)
- bloom on a white disc: ring luma 61.0 → 69.4 at strength 1.0; visible soft halo
- ACES: white 255 → 204, mid-grey patch lifts 20.9 → 25.6 (a real grade, tunable with exposure)
- toggling mid-record: halo on frames off/on/off = 0.08 / 40.3 / 0.07
- cost: same 180-frame record 6.17 → 5.73 ms/frame (inside noise; one 1080p copy + quarter-res passes)
- 16 local post/mesh tests pass; full suite: 0 new failures vs baseline

## Native

New `vulkan_post.c/h` + `post_shaders.h` (generated by `shaders/gen_post_spv.py`), exported `SetPost` on Windows and macOS, build scripts updated. The macOS dylib is rebuilt on this branch's CI and committed here; the runtime post path itself still needs a mac run (the copy uses the same `vkCmdCopyImage` transition as the existing screenshot readback).

</details>

### #145 — feat: MeshMobject - a scene mobject drawn through the depth mesh

`feat/mesh-mobject` · merge `c88e94674a`

<details><summary>PR description</summary>

Part A1 follow-up: a scene-side mesh mobject, so ordinary manim transforms move
the depth mesh.  `MeshBatch.from_surface` is a snapshot and `MeshBatch` is frame
geometry, not a scene member — a `shift`/`rotate`/`.animate` on the `Surface`
never reached it, and the previous docs told users to bake and then
`set_opacity(0)` to keep a mobject around.

## `MeshMobject`

```python
from real_time_manim import MeshMobject

surf.set_shade_in_3d(False)
surf.set_stroke(width=0)
mesh = MeshMobject.from_surface(surf)
self.add(mesh)                       # no win.set_mesh needed
self.play(mesh.animate.shift(RIGHT * 2))
```

- `Mobject` subclass whose `points` ARE the unique `(N, 3)` mesh vertices, with
  `(Q, 4)` indices and per-corner RGBA.  `shift`/`rotate`/`scale`/
  `apply_function` and `.animate` therefore edit the mesh; `to_mesh_batch()`
  re-points the batch at the current array and calls `mark_geometry_dirty()`
  when the vertex bytes changed (an unchanged frame keeps the projection
  cache).
- `MeshMobject(vertices, quads, colors=None)` for explicit geometry;
  `from_surface(surface)` reuses the `MeshBatch.from_surface` bake and its
  validation/errors.
- `MLWindow.sync` collects every `MeshMobject` in the scene (nested inside a
  `Group` too) and merges it with an explicit `win.set_mesh(...)` batch,
  identity-deduplicated, into the frame's single native mesh.
- `paint.py::_send_impl` skips the class via `_rtm_mesh_skip`; its vertices are
  mesh data, never a path.

### #146 — feat: share Scene.prepare() across recording workers

`feat/shared-prepare` · merge `e6782300ec`

<details><summary>PR description</summary>

Roadmap slice ③: frame-parallel workers no longer pay for expensive scene preparation separately.

## Problem

`jobs=N` starts one process per worker, and each worker has to rebuild the scene: manim mobjects, animations and updaters are not picklable, so the constructed scene cannot be sent across processes. Expensive pure setup (terrain arrays, meshes, layouts, parsed assets) was therefore repeated N+1 times (probe + workers).

## What changed

**`Scene.prepare()` → `prepared()`**

```python
from real_time_manim import Scene, prepared

class Film(Scene):
    @classmethod
    def prepare(cls):
        return {"verts": build_terrain()}      # picklable data only

    def construct(self):
        data = prepared()                      # loaded once per process
```

The parent record runs `prepare()` once, publishes the pickle, and every worker loads it. `prepared()` returns `None` when the scene is run without a recorder.

**`shared_prepare(key, builder, version=1)`**

A cross-process on-disk cache with an exclusive lock for builders that cannot move into a classmethod:

```python
world = shared_prepare("world-v3", build_world)
```

The first process computes and atomically publishes; concurrent processes wait for the file and load it. `version` invalidates old entries; `RTM_PREPARE_DIR` is respected as a persistent cache and otherwise a per-record temp directory is used and removed after all workers finish.

`fast_record_scene` / `record_scene` open that scope around the probe and the workers, so the payload lives exactly as long as the record.

## Honest scope

`construct()` still runs in every worker — it must, to build per-process mobjects. The shared product is the expensive *data*, which is what the feedback's "prepare" refers to. The docs say so explicitly and state the picklability contract (numpy/dicts/lists; not mobjects with lambdas).

## Verification

- `jobs=2` scene: `prepare()` ran once, a `shared_prepare` builder ran once, `construct()` ran 3× (probe + 2 workers), 12-frame output correct
- cross-process lock test: two spawned processes, builder writes a counter once, both get the same value
- unpicklable result raises `TypeError` naming the contract
- 6 new tests pass; full suite: 0 new failures vs baseline
- no native change

</details>

### #150 — feat: native lit mesh pipeline (normals + material)

`feat/mesh-lighting` · merge `588c58bbbe`

<details><summary>PR description</summary>

Roadmap slice ④a: normals and material for mesh geometry.

This sits **next to** the existing CPU-baked `shade=True` path (PRs #147/#149): `shade=True` still bakes manim's two-stop lighting into the colours, while `lit=True` keeps the base colours and sends face normals to a new GPU pipeline with a light/material model. The two cannot be combined on one mesh.

## Native

- New lit pipeline: vertices are `x,y,z,nx,ny,nz,r,g,b,a` (10 floats); fragment stage applies Lambert + optional Blinn-Phong with a two-sided normal, camera-space light direction and ambient/diffuse/specular/shininess push constants.
- `AddMeshLit` / `AddMeshIndexedLit` / `SetMeshLight` exported on Windows and macOS.
- Lit and unlit share the GPU vertex buffer (sized for the larger stride) and index buffer; each `Add*` clears the other's counts so a frame cannot mix them.
- Shaders in `mesh_lit_shaders.h` (generated by `shaders/gen_mesh_lit_spv.py`).

## Python

```python
mesh = MeshBatch(lit=True).append(quads, colors)      # flat normal per quad
mesh = MeshBatch().append(quads, colors, normals=...) # or explicit
mesh = MeshBatch.from_surface(surf, lit=True)         # Surface face normals
mesh = MeshMobject.from_surface(surf, lit=True)       # scene-side + transforms
win.set_mesh(mesh)
win.set_mesh_light(ambient=0.30, diffuse=0.80, specular=0.25, shininess=24)
```

- `append_indexed(normals=)` accepts `(N, 3)` per unique vertex (smooth) or `(Q, 4, 3)` per corner (flat).
